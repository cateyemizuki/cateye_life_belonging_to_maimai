## 五、关键技术内容

### 5.1 W1（P5）口径裁定

`affection.morning_sent()/night_sent()` 是**按天全局布尔**（affection_memory.json `morning_sent_today`，日切清零）且**仅 TARGET 类问候写入**（proactive_service.py:1191-1193 `_mark_greeting_sent_on_affection`）。若按登记行字面对群聊/其他私聊也查全局标记：「目标已发」会误判为「该流已发」——压制三类矩阵多群全发语义（预埋用例 128 必红）并污染 patrol 跨模块查重（patrol.py:275/:371-373 的语义=目标侧）。**裁定：查重限 TARGET 类**（生产 P5 即目标场景，精确修复）；非目标类的跨重载去重需按流持久化（状态形状变更）→ **登记待议**。判别性用例 d（标记置位后群聊仍正常触发）钉死该口径。

### 5.2 W2（P6）诊断先行——登记行假说证伪

主会话侦察 + 实施员离线复现共同证实：**登记行"写回被 `_normalize_items` 截断"的假说不成立**——`apply_schedule_items`（schedule_generator.py:274）不调 `_normalize_items`（其仅用于生成路径 :220），`replace_day_schedule`（schedule_db.py:142-163）原样写入，`find_current_activity`（schedule_query.py:24-49）纯槽匹配。**真因=槽位抢占**：lie-in 只延长了 sleep 条目的 end，日程里与延长窗口重叠的清醒条目（生产构造中 11:05 起）在槽匹配中命中 → `awake_activity=True` → 醒沿判定（service.py:2390 `if awake_activity or …`）抢先触发。**修法**（任务书选项的实现变体）：lie-in 写回时同步把与延长窗口重叠的当日非睡眠条目顺延/移出（tools_service 写回段）+ schedule_query 槽匹配辅助（共 90 行）；`_normalize_items` 生成路径契约未动、跨午夜不倒挂（用例 e）、正常日程零变化（用例 c）。

### 5.3 W3（R1）结论=登记待议（浓缩版，全文已回写计划书）

- **触发条件**：①生产可达——夜内重载/重启（睡眠运行期状态纯内存，on_load 重建即按 live 锚点重算整夜窗）；②生成侧可达——**默认锚点即可复现**：夜窗内清醒条目（`_normalize_items` 对 start 只设下界 :822、validator 保留告警项 :119）导致夜内早醒。宿主 4 天真实排程生成 4/4 天合规 → 实际频率低。
- **影响**：(a) 同夜双口径 woke_up（内存 elapsed vs 窗口−扰段；实测 3.17 vs 8.0，恢复档位可差 0.85/0.30）；(b) 重启丢弃 `_night_archived` → 当夜已确认打扰按 0 计、暖意不入账；(c) 已结算周期重入重发 sleep_started 不冻结 → 重入段事件双计、夜尾闭段永不 settle；(d) 挪锚+重载可双 cycle_key。危害有界（不崩溃、不坏状态文件）。
- **待裁三点**：①重入口径（锚点整夜【现状】vs 截到重入时刻 vs 混合）；②`_publish_sleep_started_if_needed` 是否加"已结算周期不再宣告"守卫；③`ended_cycle` 取值时序（**须与①同批裁**——单独改会让同一 cycle_key 二次结算，破坏附录 §2.3 契约）。
- **生成侧护栏缺口**：start_minute 仅下界 + validator 保留告警项 → 夜窗内清醒条目可经正常生成入库（P6 的 W2 修复只覆盖 lie-in 写回段）。
- **确认员纠正**（对抗复核价值）：分析员原判"夜窗清醒条目仅 L4/带外写入可达"被实跑复现证伪（默认锚点+常规生成形态即可），且 `_night_archived` 有 128 上限（非无界）、恢复分档表摘要补全（5-6h→0.60 档）、场景 1(b) 补记 L1 记账死区。
